# One three-layer system: implemented projection and remaining gates

The fundamental perspectives are Practical reality, Academic/explanatory knowledge, and Implementations/solutions. Discovery sources are attached as provenance, not counted as a fourth conceptual layer. Commercial arbitrage is downstream analysis, not another foundational layer.

## What actually works now

The code reads the existing development-only primary-source mechanisms and institutional requirement-to-repository assessments, then normalizes them to one typed three-layer **read-only query view**. Original source/README provenance and candidate-vs-reviewed status remain explicit. A user can query a problem to retrieve proposed explanations, implementation leads and missing perspectives without inventing connections.

The bounded snapshot has 21 practical records, eight academic mechanism hypotheses and 21 implementation leads. Seven problem records have all three perspectives represented. **Zero end-to-end solutions, paying buyers or economic margins have been verified.** A structurally complete chain is not field validation.

Battery recycling has the three perspectives represented, but no localized tested recovery plant. An Italian institutional energy requirement has a possible metering-protocol component, but no mechanism-level research connection in the current sample. Gig-worker safety is left without an implementation instead of being force-matched to social monitoring tools.

## Remaining engineering sequence

1. **Native storage integration with source-review promotion gates.** This PR is a read-only projection, not a migration to the persistent SemanticGraph. Native code uses program for implementation and permits neutral metadata nodes. Align the conceptual layers, keep provenance attached separately, and require an explicit review before upgrading existing edge statuses. The existing add_edge API can otherwise overwrite an earlier status on a repeat call.
2. **Bidirectional investigation queries.** Retrieve problem -> mechanism -> possible implementation, and implementation -> potentially relevant problems, caveats, alternatives and missing links. The current projection has a problem-ID query but no production reverse traversal.
3. **Independent entailment review.** Check if the exact original source supports the proposed claim, whether the mechanism transfers across contexts, and whether there is contradictory evidence. Hash and quotation checks alone do not prove the meaning.
4. **Executable component-fitness checks.** Run bounded third-party components against representative workflows and measure failure behavior, deployment constraints, licensing and maintainability. README claims are not interoperability proof.
5. **Expand practical problem/cost evidence across fields.** Use problem-first plus technology-first discovery; do not turn GitHub search relevance or procurement titles into market conclusions.
6. **Conversion assessment downstream.** Independently establish buyer, permission, total service/failure costs, margin, and maintained operating value. No economic winners should be announced prematurely.
