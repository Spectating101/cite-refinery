# YZU Existing Workflow Fit Evidence V0.1

Date: 2026-09-09

Purpose: establish whether the proposed Problem Commons pilot overlays a real YZU operating need or invents an artificial workflow.

## Current YZU workflow evidence

YZU's 2025 University Social Responsibility annual report describes an explicitly **platform-based and issue-oriented** operating model for connecting external practice fields with university resources.

The report states that YZU uses:

- a digital supply/demand matching area on its sustainability site;
- proactive campus-wide distribution of field needs when a local partner requests support;
- a maintained **field cooperation history and needs database**;
- periodic collection of partner lists, available support, and unresolved field difficulties from USR teams;
- reuse of that database when new social-participation courses or USR Hub teams need a field/problem to work with;
- internal Far Eastern Group resources and external corporate resources to support field work.

Source:
https://esdg.yzu.edu.tw/media/attachments/2026/04/01/114--6-65.pdf

The same report identifies two core fourth-phase USR projects and six USR Hub projects, giving the Center a recurring portfolio rather than a single one-off field-matching case.

YZU's public `場域媒合` page independently confirms the public-facing part of the workflow: communities, schools, nonprofits and public/private organizations can supply needs, and YZU faculty/students are invited to find collaboration opportunities against them.

Source:
https://esdg.yzu.edu.tw/index.php/tw/2025-11-28-08-49-26

## Implication for the pilot

Problem Commons should **not** pitch itself as YZU's new demand database.

The testable value is downstream of the database YZU already describes:

`existing field/history/needs database`
`→ preserve source + freshness + owner-confirmation state`
`→ owner-reviewable Problem`
`→ bounded work / Project Briefs`
`→ solver/resource matching`
`→ attempt + review`
`→ outcome / continuation / reusable capability`

## Smallest useful integration assumption

Cycle 1 should require no API or platform integration.

A Center export containing only:

- title;
- potential owner/field partner;
- current need statement;
- geography;

is sufficient to create restricted intake candidates. Everything else can remain unresolved and be asked during owner review.

The batch CSV template is:

`pilot/intake/yzu-center-batch-template.v0.1.csv`

## Falsification

The institutional-fit hypothesis is weakened if any of the following occurs:

- the described needs database is no longer actively used;
- existing needs are already consistently specific, current, owner-confirmed, solver-ready and longitudinally tracked, leaving Commons little incremental value;
- owner review adds ceremony without materially improving matching or outputs;
- the Center cannot nominate even one current unresolved need suitable for external student/research work;
- a normal spreadsheet/manual workflow produces equivalent outcomes with less overhead.

The annual-report description is evidence that an adjacent workflow exists. It is **not** evidence that YZU wants, needs, or has adopted Problem Commons.
