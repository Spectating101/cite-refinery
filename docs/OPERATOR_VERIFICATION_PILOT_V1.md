# Operator Evidence Verification Sprint — proposed limited commercial pilot

**Status October 21, 2026: proposed service, executed technical demo, zero verified buyers, accepted prices, contracts or revenue.**

## The customer's decision

"Can I trust this technical claim or implementation enough to invest in a fix, integration, or deployment?"

The first productized Cite–Refinery offering should be a **human-reviewed evidence-to-decision sprint**, not a speculative general-purpose research SaaS, automated security certification, or a claims-generating opportunity dashboard.

The three-layer investigation distinguishes Practical operator reports, Academic explanations, and Implementation code. It then assesses whether they actually belong together, whether the *original* function has been tested, and precisely which test or permission is still missing. Matching a publisher text is not proof of true field outcomes; passing a scoped candidate test is not full integration.

### Who could pay

Start with technical founders and small software teams deciding whether to repair an inherited integration; agencies reviewing a subcontractor's delivery; or funded academic/NGO technical operations facing a real procurement or engineering decision. **Unfunded open-source maintainers are not assumed buyers** merely because they reported GitHub issues.

The difference from a generic AI response is a shareable, source-pinned decision: actual reporter statement, independent mechanism-scope assessment, real original-source execution when permitted, a bounded patch regression, and a falsifiable next step.

## One narrow intro offer

**Hypothesis to test: US$490 fixed** for one client-authorized repo/problem, up to two contextual scholarly sources, a short evidence review, a bounded original component reproducer where feasible, and one executive decision brief. **Maximum six engineering hours**; not a commitment to finish an app upgrade. If reproducing the defect exceeds the limit, deliver an explicit technical blocker and offer a separate quote for the integration.

This is a *price experiment*, not current revenue or established market willingness to pay. The client must approve scope, code access and any use of third-party materials.

## Demonstrator

An actual existing investigation was run over published Open Food Network and Foodsoft issues, two original source code files, and academic papers. Existing original-browser Jasmine and original-helper Ruby RSpec test receipts are joined by *exact Git blob identity* to authenticated Implementation sources. The productized brief accurately distinguishes:

- A plausible but unresolved OFN geocoding mechanism and an experimental source-level regression (original 10/14 vs local patch 14/14; full original app, zoom and actual viewport untested).
- An unrelated heat-warning academic link to that same OFN code, rejected despite the bounded technical tests.
- A geocoding academic link to Foodsoft order precision, rejected despite the separate bounded Ruby precision improvement (original 6/9 vs temporary local patch 9/9).

See OPERATOR_DECISION_DEMO_V1.md and research_materials/opportunity_atlas/operator_decision_demo_v1.json. These are generated from previously obtained evidence, not a new source-code execution or newly validated human outcome. Neither upstream repo has accepted a fix.

## Concrete acquisition experiment

**Five discovery conversations:** ask decision owners about an ongoing engineering uncertainty, current cost of verifying it, permission to inspect and execute the code, actual stakeholder who can purchase, and decision criteria. Log refusals.

**Two scoped proposals:** offer the US$490 fixed pilot on permissible data with written authorization and clear exclusions. Obtain approval before work or payment. Resolve applicable employment/work authorization, client rights, confidentiality and invoicing requirements. Do not perform anonymous scraping of private systems or intrusive outreach.

**Continue only on evidence:** at least one paid and *used* decision brief, independently reviewed material accuracy, bounded effort, and an operator who says what decision changed. If five conversations and two real proposals yield no sales, revisit the buyer/outcome before adding more product features.

Only after repeated use should SaaS, subscriptions, automatic background monitoring or deeper integration be considered. Record actual delivery hours and collected fees rather than counting users who compliment a demo.

## Hard exclusions and boundaries

Not a penetration test, legal/licensing certification, investor due diligence assurance, peer-reviewed proof, production integration acceptance, or guaranteed software fix. Real application configuration, sensitive data, upstream PR submission and ongoing support require separately approved work.

No new standalone CLI, no fourth foundational conceptual layer, no additional campaign-specific core engines. Consolidate duplicate wrappers only after caller and behavior-parity checks. The current source-backed demo is limited to **previously verified OFN and Foodsoft code blobs**. General executable test ingestion for arbitrary repositories is a later gate, not a claimed existing feature.
